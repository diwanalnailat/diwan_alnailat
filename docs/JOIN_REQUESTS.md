# Membership applications

Open `/join` from the heritage page. Applicants provide their name, WhatsApp phone, reason and committee (or direct Diwan membership), read the current policy and consent. Active-project committee names are the only committee data exposed publicly. If none exist, the form submits directly to the Diwan.

Optional attachments: one identity file and previous-experience files, accepting every format, up to 6 files, 100 MiB per file / 300 MiB total. A separate mandatory attestation confirms data accuracy, ownership of documents and conformity with their originals. Its exact text/time and immutable file manifest (kind, name, original size, ordered SHA-256 checksums of 3 MiB parts) are saved with the policy snapshot when requesting OTP. Hashing reads one part at a time, without loading all files into browser memory.

The browser retains files locally until OTP verification. `POST /auth/join/verify` with `upload_mode: "chunked"` consumes the browser-bound code once and opens a one-hour upload session; the request stays `verifying`, hidden from reviewers. Subsequent `chunk?file=N&part=N`, `upload-status`, and `complete` POSTs require the HttpOnly browser binding plus HMAC capability in `x-join-upload` and challenge in `x-join-challenge`. Each raw part is bounded and checked against the consented manifest before writes. The server gzip-compresses parts losslessly only when smaller; incompressible data stays raw. No image resampling, PDF rewriting or applicant-archive extraction occurs. Compression savings depend on the content.

Verified parts use private `nl_files` staging rows (`join_upload`). Retry status fetches only the current request's part indexes; already committed parts are skipped. Concurrent duplicate uploads retain one object. Completion requires every expected part and atomically promotes the request, creates logical file metadata, marks parts `join_parts`, and queues reviewer notices once. Lost verification/completion responses are retryable; resumption requires keeping the page/files open and the session unexpired. Staged and internal part rows are never downloadable, including by administrators. Older bounded multipart clients remain supported with the original 4 MiB body bound.

Failure cleanup deletes only uncommitted objects and preserves committed objects after uncertain responses. Maintenance removes abandoned staging rows/objects older than 24 hours in batches of 200; deletion failures retain rows for retry. Exceptional objects whose Storage write succeeds while the metadata/cleanup services both fail still need operational reconciliation; errors are logged without personal payloads.

`GET /join-requests?id=...` includes attachment metadata only for authorized Diwan administration. Review lists do not fetch files. Committee supervisors and applicants cannot list/download these attachments. Downloads go through the authorized `/api/files/:id` route with no-store, nosniff, application/octet-stream and attachment disposition, including when `inline` is requested. No active-format preview or content extraction occurs. Older requests without an attestation remain readable and are labeled accordingly; an old unsubmitted OTP draft requires a fresh request with attestation.

Supabase attachments use the dedicated private `diwan-join-files` bucket, created explicitly by `node --env-file=.env.local scripts/setup-join-storage.mjs`. Its 4 MiB object cap remains unchanged: each stored part is at most 3 MiB. All formats are allowed only in this bucket; existing `diwan-files` restrictions remain unchanged. Each upload remains below [Vercel's function payload limit](https://vercel.com/docs/functions/limitations#request-body-size). Authorized downloads use a dedicated 300-second Next route and [stream responses](https://vercel.com/kb/guide/how-to-bypass-vercel-body-size-limit-serverless-functions), decompressing/checking one part at a time and returning the byte-identical original filename/content, without whole-file server buffering. Existing `nl_files` metadata and `nl_join_requests.policy_snapshot` are reused; no schema migration is required. The original Worker/R2 and local SQLite backends use their existing private BUCKET when JOIN_BUCKET is absent.

`/auth/join/request` sends a browser-bound six-digit OTP, valid for five minutes with five attempts and per-phone/IP/global limits. `/auth/join/verify` consumes it atomically and publishes the application to the administration queue. Drafts do not create accounts or appear in review lists. One pending/referred request per phone is enforced by a partial unique index. The accepted policy version, snapshot, timestamp and phone-verification timestamp are retained. Stale policy versions require new consent. Maintenance removes unverified drafts older than one day; existing maintenance scheduling requirements remain unchanged.

The sidebar contains **طلبات الانضمام** and **شروط وسياسة الانضمام**. Global `users/manage` administrators can review all applications, approve/reject directly, edit policy, or refer a committee application to its current active manager automatically. No separate supervisor selection is required; a supervisor membership title does not grant application-review authority. Direct Diwan applications cannot be referred. The manager sees and decides only applications specifically referred to them while their manager assignment and committee access remain valid. After a manager change, administration re-refers pending applications to the new manager. Explicit denies still apply. Referral, approval and account/membership creation use version guards and atomic batches.

Approval creates an active, phone-verified application member with the submitted name and no global grants. Committee applicants receive the existing ordinary-member permissions for that committee only. Existing accounts are reused without replacing privileges; suspended accounts must be handled in member administration. Login uses the existing WhatsApp server session flow, so a Supabase Auth user/email is not required for a new member. Rejection creates no account.

Approval also atomically queues an in-app acceptance receipt and a WhatsApp receipt for the applicant. The text is `تم قبول طلب انضمامك إلى ديوان النائلات من مشرف اللجنة.` for a committee supervisor/manager, or `تم قبول طلب انضمامك إلى ديوان النائلات من إدارة الديوان.` for an administrator. Version guards prevent duplicate receipts when a decision is replayed. Reading one's approved receipt does not expose the application review queue; its link opens the member profile. Delivery rechecks active status, verified phone and the accepted request's member/phone match. New members without contact preferences receive this transactional receipt; an existing WhatsApp opt-out is respected. No message is queued for rejection. Provider acceptance is distinct from confirmed delivery.

Verified applications enqueue in-app admin notices and WhatsApp notices through the existing outbox. The configured active administrator matching `DIWAN_ADMIN_PHONE` receives the explicitly requested operational notification without requiring an unrelated user notification preference. Other eligible administrators use their saved WhatsApp preferences. Green API receives only `يوجد طلب انضمام للجنة … بانتظار ردكم.` or `يوجد طلب انضمام للديوان بانتظار ردكم.` No applicant name, phone or reason leaves the platform in that notice. Provider acceptance is recorded; delivery confirmation is not inferred. No test WhatsApp messages were sent during implementation.

Schema: generated PostgreSQL migration `supabase/drizzle/0003_join_requests.sql`, corresponding historical-compatible SQLite migration `drizzle/0006_join_requests.sql`. The PostgreSQL migration was applied to the existing connected database on 2026-09-20; `nl_join_requests` has RLS, zero anon/authenticated grants and server-only access. There are no new Storage, Realtime, Edge Function, view or SECURITY DEFINER changes. Do not rerun the initial schema.

Committee forms can save a custom membership title under Other. Titles are retained in the existing server-only settings table for future forms and never confer permissions by name. A pending inline person may be selected for both leadership and explicit membership; saving creates distinct role notices with one shared single-use credential. Authority is the union of the authorized assignments/grants, with explicit denies and expense approval conflicts still taking precedence.
